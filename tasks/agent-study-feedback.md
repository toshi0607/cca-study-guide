## F-1. 学習者の進捗をエージェントが読む手段が手動コピペしかない

- **問題**: サイトの進捗は localStorage のみ。伴走するエージェントが「どのカードが
  未習・弱点か」を知るには、利用者が 進捗ビュー → JSON エクスポート → チャットへ貼付、
  という手作業を毎回はさむ必要がある。
- **根拠**: セッション1の開始時点。学習者の状態が分からないので、加重サンプリングの
  診断テストから始めるしかなかった（本来なら弱点ドメインから始められる）。
- **提案する機構**: エクスポート JSON を「エージェントに渡す用」として最適化する。
  現状の完全なスキーマではなく、`弱点ドメイン / 誤答の多い card ID / 直近の due 件数`
  に絞った短い要約テキストをワンクリックでコピーできるボタン（例: 進捗ビューに
  「学習状況を要約してコピー」）。外部送信はせずクリップボードのみ。制約
  （学習内容・進捗を外部送信しない）を守ったまま伴走の初期コストが消える。
- **状態**: **実装済み・本番反映済み**（PR #72 / `claude/agent-study-feedback-9f5fb0` → origin/main、2026-08-11 確認）

## F-2. 2台運用（PC + スマホ）で進捗が合流できない

- **問題**: import は完全置換でマージしない（`src/components/App.tsx:164` の
  `studyStorage().save(imported.data)`。VERIFIED）。PC とスマホの両方で学習すると、
  後から import した側の進捗（reviews / quizStats / mock-exam attempts すべて）が
  上書きで消える。結果として「1台を正に決めて、もう1台は記録を諦める」しか安全な運用がない。
- **根拠**: セッション1（2026-08-10）。学習者が「PCとスマホで勉強する」と明言したので
  運用を設計しようとしたが、無損失に合流する手段が無く、スマホを正・PCの演習結果は
  エージェント側のログへ手書き、という回避策を取らざるを得なかった。
- **提案する機構**: import に**マージモード**を足す。サーバー不要で成立する。
  - `reviews`: 同じ card ID は `dueAt` が新しい方、または `lastReviewedAt` が新しい方を採用
  - `quizStats`: 回答数・正答数を単純加算（同一 attempt の二重計上を避けるなら attempt に ID を持たせる）
  - `mock-exam attempts`: attempt ID で和集合
  - UI は import 時の確認ダイアログに「置き換える / 統合する」の2択を出す。
    既存の置換動作は残す（現在の挙動に依存している利用者のため）。
  - スキーマ互換性の契約は壊さない。マージは読み取り側の関数を足すだけで済む。
- **状態**: **実装済み・本番反映済み**（PR #72 / `claude/agent-study-feedback-9f5fb0` → origin/main、2026-08-11 確認）

## F-3. 学習ガイドに所要時間はあるが「締切から逆算した割り付け」が無い

- **問題**: `study-guide.ts` の8セクションには `estimatedMinutes`（合計360分）と
  `recommendedOrder` があるのに、サイト上には「受験日まで何日で、今日どこをやるべきか」を
  出す導線が無い。今日ビューが見せるのは due カード数であって、ガイド消化の進度ではない。
- **根拠**: セッション1。受験日 9/5・残り26日という条件で週次プランを組んだが、
  その計算（360分 ÷ 残り週数、弱点ドメインを前倒し）はすべてチャット側で行い、
  サイトには何も残らなかった。次のセッションでボクが同じ計算をやり直すことになる。
- **提案する機構**: 進捗ビューに**受験予定日の入力**（localStorage、任意・空でよい）を足し、
  今日ビューに「残りN日 / ガイド未消化M分 / 今日の推奨セクション」を出す。
  合否や準備完了度は一切示唆しない（絶対的制約）ので、出すのは
  **消化済み分数と残り日数という事実だけ**にする。
- **状態**: **実装済み・本番反映済み**（PR #72 / `claude/agent-study-feedback-9f5fb0` → origin/main、2026-08-11 確認）

## F-4. 演習は正誤しか記録せず「たまたま正解」を見分けられない

- **問題**: `QuizStat = { attempts, correct, lastAnsweredAt, lastCorrect }`
  （`src/lib/storage-schema.ts:19`。VERIFIED）。正誤しか持たないので、
  **「確信を持って正解」と「勘で正解」が同じ1件**として積まれる。
  カード側の `練習` は `もう一度 / 難しい / できた` の3段階評価で自己申告の確信度を
  取れているのに、`演習`（quiz / シナリオ / 模試）にはその軸が無い。
- **根拠**: セッション2（2026-08-10）。学習者本人が診断5/6の直後に
  「試験用に勉強したこともドキュメントを読んだこともないので、正解もたまたま感がある」と
  申告した。サイトの記録だけを見ていたら D3 以外は「理解済み」と誤判定していたことになる。
  ボクは対話で拾えたが、サイト単独で自学するとこの情報はどこにも残らない。
- **提案する機構**: 回答送信時に確信度を1タップで添える。
  - `QuizStat` に `lastConfidence?: 'sure' | 'unsure' | 'guess'` と
    `guessedCorrect: number`（勘で正解した回数）を足す。既存フィールドは変えないので
    ストレージ互換性の契約は壊れない（v2 の任意フィールド追加）。
  - 弱点分析（`src/lib/weakness.ts`）が「正答率は高いが確信度が低い」トピックを
    拾えるようになる。これは**合否や準備完了度の示唆ではなく、自己申告の再確認対象**なので
    絶対的制約に抵触しない。
  - UI は正誤表示の直後に「確信あり / 迷った / 勘」の3ボタン。スキップ可。
- **状態**: **実装済み・本番反映済み**（PR #72 / `claude/agent-study-feedback-9f5fb0` → origin/main、2026-08-11 確認）

## F-5. 複数選択の部分正答が、全誤答と同じ「不正解1件」として記録される

- **問題**: `isCorrect` は集合の完全一致（`src/lib/quiz.ts:44-45`。VERIFIED）。
  2つ正解のうち1つだけ選んだ「あと一歩」と、誤答2つを選んだ「理解していない」が、
  `QuizStat` 上は同じ `correct` 非加算として積まれる。
  選択肢ごとの解説（`ChoiceReview`）は表示されるので**その場では分かる**が、
  弱点分析に渡る記録には粒度が残らない。
- **根拠**: セッション2（2026-08-10）。学習者が `q-sc-code-skill`（正解 a,d）に
  a のみで回答。ボクは「概念は掴めているが選び切れていない」と診断できたが、
  サイトの記録上は全誤答と区別がつかない。
- **提案する機構**: `QuizStat` に `partial: number`（正解の部分集合のみを選び、
  誤答を1つも含まなかった回数）を足す。F-4 の確信度と同じく任意フィールド追加で、
  ストレージ互換性の契約は壊れない。弱点ビューで「惜しい」と「未理解」を分けて出す。
- **状態**: **実装済み・本番反映済み**（PR #72 / `claude/agent-study-feedback-9f5fb0` → origin/main、2026-08-11 確認）

## F-6. 模試の出題数 = 問題バンク全体。演習で消化すると模試が「初見」でなくなる

- **問題**: `MOCK_EXAM_QUESTION_COUNT = 60`（`src/lib/mock-exam-blueprint.ts:14`）に対して
  `questions.ts` のバンクも**ちょうど60問**。ドメイン配分 d1:16 / d2:11 / d3:12 / d4:12 / d5:9 も
  バンクの各ドメイン実数と完全一致していて、**余剰がゼロ**（VERIFIED）。
  つまり模試は毎回バンク全体を出題する。日々の `演習` で問題を解くほど、
  模試の測定としての価値（初見での実力把握）が削れていく。しかも学習者には
  その消耗が見えない。
- **根拠**: セッション2（2026-08-10）。受験日から逆算した計画を組もうとして、
  1日で14問（バンクの23%）を消化済みだと気づいた。「弱点ドリルを毎日やる」という
  自然な学習計画が、そのまま模試を無価値にする構造になっている。
  結果、**問題を温存してカード・シナリオ中心で進める**という不自然な計画を組むはめになった。
- **提案する機構**（安い順）:
  1. 模試の開始画面に「この模試に含まれる60問のうち **N問は演習で回答済み**です」と
     事実だけ表示する。合否や準備完了度の示唆ではないので絶対的制約に抵触しない。
     `quizStats` の既存データだけで実装できる。
  2. `演習` の出題設定に「模試用に未出題の問題を残す」トグル（残す問数を指定）。
  3. 根本解決はバンク拡張（60 → 90以上）。ただしコンテンツ制作コストが高いので、
     1 を先に入れて消耗を可視化するのが費用対効果がよい。
- **状態**: **実装済み・本番反映済み**（PR #72 / `claude/agent-study-feedback-9f5fb0` → origin/main、2026-08-11 確認）

## F-7. 学習パスの8ステージにコストの重みが出ておらず、ステージ3で計画が壊れる

- **問題**: `learning-path.ts` の8ステージは順序だけを持つ。ところが実コストは桁違いで、
  ステージ3のハンズオンは **4本で480分**（`hands-on.ts` の `estimatedMinutes` 合計 120+90+120+150）と、
  ステージ2の学習ガイド全体（360分）より重い。順番に進む導線なのに、
  **ステージ3が全体の最大の時間投資であることがどこにも表示されない**。
- **根拠**: セッション2（2026-08-10）。学習者が「ハンズオンってやらんくても大丈夫？」と
  自分から聞いてきた。コストが見えていれば聞く必要のない質問で、逆に言えば
  **見えていないから不安になっている**。ボクが `estimatedMinutes` を合計して初めて
  「25日の学習枠に対して480分は重い」と判断できた。学習者はこの計算をする手段を持たない。
- **提案する機構**:
  1. 学習パスの各ステージに**その配下コンテンツの `estimatedMinutes` 合計**を表示する。
     ガイド360分 / ハンズオン480分 / 模試120分 は全部データとして既にあるので、合計するだけ。
  2. ハンズオン一覧に各ガイドの所要時間を出す（詳細に入る前に分かるように）。
  3. 合否や準備完了度は一切示唆しない。出すのは**所要時間という事実だけ**なので
     絶対的制約に抵触しない。
- **備考**: 「実装する／読むだけ」の2モードは学習者側の運用で回避できるので、
  機構としてはコスト表示だけで足りる。まず1を入れるべき。
- **状態**: **実装済み・本番反映済み**（PR #72 / `claude/agent-study-feedback-9f5fb0` → origin/main、2026-08-11 確認）

## F-8. どのコンテンツにもディープリンクが無く、宿題を URL で渡せない

- **問題**: サイトは単一ページ + 内部 state のビュー切り替えで、URL は `/` `/en` `/privacy` の3つだけ。
  `src/components/` 内の `window.location` は**全て `.reload()`** で、hash も query も
  `history.pushState` も使っていない（VERIFIED）。したがって
  **特定のカード・セクション・ハンズオンのステップを指す URL が存在しない**。
- **根拠**: セッション2（2026-08-10）。ボクが宿題として
  「`ho-support-agent-escalation` の `step-loop` を読んで」と出したら、学習者から
  **「これ何の話？リンクある？」**と返ってきた。渡せる URL が無いので、
  「ガイドタブ → 学習パスのステージ3 → エスカレーション型エージェント → 該当ステップ」という
  **手順の説明**を書くしかなかった。内部 ID（`ho-support-agent-escalation` / `step-loop`）は
  リポジトリの用語であって、UI 上にはどこにも表示されないため、学習者には意味不明な文字列になる。
- **影響範囲**: 伴走エージェントに限らない。学習者が自分でブックマークすることも、
  SNS や勉強会で「この解説が良い」と共有することも、スマホと PC で同じ場所を開くこともできない。
  F-2（2台運用）とも複合する。
- **提案する機構**: hash ベースのディープリンク。ルーティングフレームワークは不要。
  - `#/hands-on/ho-support-agent-escalation/step-loop` `#/practice/d1-stop-truncation`
    `#/guide/sg-agentic-loop` のような形式で、既存の「ビュー + target ID」の仕組み
    （`QuizView.targetScenarioId` / `HandsOnView.targetGuideId` など、既に存在する型付きターゲット）に
    hash を読み書きするだけ。静的サイトのままで成立する。
  - 各詳細画面に「リンクをコピー」ボタン。
  - 永続化された content ID は互換性契約なので、URL に載せても壊れない。むしろ
    **ID が既に安定契約であることがこの機能の前提を満たしている**。
- **状態**: **実装済み・本番反映済み**（PR #72 / `claude/agent-study-feedback-9f5fb0` → origin/main、2026-08-11 確認）
