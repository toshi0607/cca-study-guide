# Lessons

- For non-essential privacy UI, confirm the intended audience, regulatory posture, and acceptable UX interruption before choosing the strictest implementation. Present the trade-off between opt-in consent and clear disclosure before making the choice part of the product.
- When acknowledging a content revision, preserve historical timestamps that have no separate audit field. Use `updatedAt` for the acknowledgement time and change only the revision/status fields required by the explicit transition; never repurpose or overwrite the sole original completion timestamp.
- For content-ID-driven UI, never use a non-null assertion on authored IDs. Validate every branch against the real content set, render human-readable localized labels instead of bare IDs, and test every selectable branch.
- Lazy-loading a heavy view is not enough on its own: if the parent (App) statically imports the feature's engine/domain logic to build callbacks, that logic still ships in the initial landing bundle and can regress FCP/LCP even though the view component itself is a dynamic import. Keep the parent free of domain imports — pass a generic storage bridge (readData/writeData) down and let the lazily-loaded view own all engine calls and imports. Verify with a matched main/branch Lighthouse on the same machine (a single-side number is not evidence), not just the entry-chunk size.
- Exact-target navigation must define how focus is transferred after the source view unmounts and how the user exits the target mode. Provide an announced focused destination plus an explicit path back to normal browsing, and cover both in end-to-end tests.
- Treat persisted content IDs as compatibility contracts. When splitting or reorganizing content, keep the closest semantic successor on the existing ID with a new revision, and let newly split sections start untouched; never duplicate one historical completion across multiple new records.
- In a git worktree session, ALWAYS use the session worktree base path (`.claude/worktrees/<session>/…`) for Read/Edit/Write. Bash runs in the worktree cwd (relative paths correct), but an absolute path pointing at the MAIN checkout reads a different, possibly stale branch. Symptom: Read line-count disagrees with `wc -l`, or Read returns "file does not exist" for a file `find`/`ls` shows. Fix: prefix every absolute file path with the worktree root, and cross-check Read against `wc -l` when in doubt.
- Never author a card's factual claim from memory of an official page. Fetch the cited section, quote the behavior, then set that card's `verifiedAt` to the day you actually read it. `d1-hook-exit-codes` shipped with "exit 2 makes the JSON ignored", but the reference says exit 2 blocks *even with* JSON (an `allow` decision cannot override it) and the reason carried by a blocking decision in that JSON becomes the blocking message, with stderr used only when no such reason is supplied — a learner studying that card would have learned the inverse. Watch the guide-vs-reference split too: `hooks-guide` is the tutorial, and the exit-code semantics live in `hooks` (the reference), so cite the page that actually states the claim.
- Correcting what a card *asserts* is not a wording edit: bump that card's `revision` (and mirror it in `card-index.ts`) so `isDue` sees `cardRevisionSeen !== revision` and pulls the card back for everyone who already studied the superseded claim. A correction that leaves `revision` alone never reaches the learners it was written for — they are scheduled far in the future on the wrong fact.
- Before declaring a PR merge-ready, fetch the base branch and compare its remote OID with the PR API's `baseRefOid`; do not treat a previously `CLEAN` mergeability result as durable. If they differ, integrate the fetched base and re-query mergeability after pushing, because GitHub can report either a stale base snapshot or a real newly introduced conflict.
- `tasks/todo.md` is an accumulating log, not a scratch file: new task plans go ON TOP of the existing content with a `---` divider, never via a fresh Write. A Write that "succeeds" can still be an unread overwrite (the 2026-08-16 MCP-server session destroyed 311 lines of task history this way and only caught it because the commit diff showed ~300 deletions). Before writing any file you did not create this session, Read it — and after committing, read the diff stat: an unexpected deletion count is the overwrite alarm.
